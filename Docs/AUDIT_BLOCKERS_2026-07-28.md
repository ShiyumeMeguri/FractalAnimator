[BLOCKER] Error certificate charges the orbit-table term as ulp·|Z| and amplifies it every step — nothing can certify at the shipping iteration count
   `error = ExpansionMagnitude[n]*error + T.RelativeUlp*offsetMagnitude + orbit.TableRelativeUlp*referenceMagnitude`. The third term injects ulp·|Z| ≈ ulp·O(1) EVERY step and is then multiplied by ∏|f'| for the whole remaining trajectory. With the map's measured λ=1.6 (0.204 digits/step) the bound after N steps is ulp·1.6^N. At DD (1e-31) that exceeds any usable margin past ~150 iterations; at QD (1e-62) past ~305 — the doc's own §2.2 budget table. `--corruptionvideodeep` defaults to iterations=400 (Program.cs:684) and DeepCorruptionLoader passes p.Iterations straight through, so EVERY interior pixel and every deep exterior pixel returns NeedsHigherPrecision at all five implemented rungs. Note the doc contradicts itself: §2.2 derives the injection as ulp·|δ_n| (which telescopes to N·ulp·|δ_final| and is harmless), while §2.4 writes ulp_table·|Z_{n+1}| — the implementation faithfully implements the fatal one. The current engine has no equivalent term and colours every pixel.

[BLOCKER] Uncertified pixels are never written to the output buffer — no fallback colour, no throw
   `RunRung` writes outputRgb only when the verdict is not NeedsHigherPrecision; after the QD rung, survivors are counted into `stats.Uncertified` and the function returns normally. Those pixels keep whatever the caller's float[] held — for a fresh `new float[w*h*3]` that is 0,0,0 → black speckle in the frame, silently. The engine being replaced guarantees a complete image: DeepOrbitTrapEngine.RepairGlitches:493-497 paints any still-glitched pixel with the best-effort interior colour `WriteColor(..., 0.0, maxIterations, 1.0, ...)`. Combined with finding 1 this means the certified renderer's first real frame is mostly black and nothing in the pipeline reports it — DeepCorruptionImage.Render just converts the buffer to a Bitmap and hands it to ffmpeg.

[BLOCKER] Colouring parameters (leafOffset, colorR/G/B) and the escape-time colouring mode are runtime inputs today, but IColoringAtom has no payload — the microkernel cannot express them
   IColoringAtom declares only `static abstract` Accumulate/Resolve/IsCertified — no instance state and no payload parameter, unlike IFractalAtom which reaches `orbit.Payload`. BStyleTrapAtom therefore hardcodes `ExponentR/G/B = 10.0/2.5/0.75` and `LeafOffset = 0.59`. Today all four are per-render values on ShaderColorParams (Core\ShaderFractal.cs:16-19) and are genuinely varied: SelfTest.ShaderGallery uses ColorR/G/B = 0.785/8.218/9.999 (Program.cs:1201) and DeepOrbitTrapEngine.Render takes leafOffset/colorR/colorG/colorB as arguments (Core\DeepOrbitTrapEngine.cs:334-337). Worse, `Render(..., bool orbitTrap)` (L337, L389) supports a second colouring mode — `outer = orbitTrap ? trap : 0.0`, i.e. pure escape-time colouring — which SelfTest.DeepJulia exercises for four zoom levels (Program.cs:1277-1278). The new architecture has no expression for any of it; the doctrine's 'no capability may exist that the microkernel cannot express' fails here. Fix: give IColoringAtom the same opaque payload channel IFractalAtom already has.

[BLOCKER] BStyleTrapAtom clamps smoothIters, converting today's NaN→black pole pixels into a real (wrong) colour
   New: `t = -0.25*TrapMin + 0.9*Math.Log2(Math.Max(smoothIters, 1e-12)) + 0.5`. Current: BStyleColoring.ColorFromTrap:161 has no clamp — `Math.Log2(smoothIters)` with smoothIters ≤ 0 yields NaN/−Inf, which propagates through ColorBand's Pow to NaN and is quantised to byte 0 (black) by every consumer (DeepCorruptionLoader.cs:78, Program.cs:1315, FractalStressHarness.cs:491). smoothIters ≤ 0 is reachable exactly where the doc's D7 pole channel lives: smoothIters = iters − log2(log2(zz)) + 3.3219, so it goes non-positive at iters=1 once zz ≥ 2^20 ≈ 1.05e6, i.e. whenever an orbit point has |z| < 0.045 and z^p (p=−2.23) explodes past 1e3. The clamp turns log2(1e-12) = −39.86 into a finite t, producing a saturated band colour instead of black, and `IsCertified` will happily certify it because the uncertainty is finite. This is precisely the class of silent image change the 0.343 fidelity gate exists to catch, and it defeats it.

[BLOCKER] Framing correction (§2.3 centre-rounding remainder) is unimplemented and unrepresentable in the renderer's signature
   D1 removes the `zooms*0.30103` term from the orbit precision, and the doc says the resulting framing error is cancelled by folding the exact AP rounding remainder of the centre into every pixel's δ_c. CertifiedRenderer.Render takes only (baked, zooms, width, height, maxIterations, outputRgb) — there is no channel for that remainder, and it computes δ_c purely as `(x - centerX) * offsetToDelta`. Meanwhile the table keeps Z_0 to just 4 limbs (~62-64 digits) and Narrow<T> then rounds further to the rung. At zoom 340 the pixel spacing is ~1e-102, so a 1e-62 truncation of Z_0 displaces the frame by ~1e40 pixel widths — a completely different location than the caller asked for. The old engine masked this by carrying `zooms*0.30103` digits in the AP context, but it too stores the orbit only at DoubleDouble (DeepOrbitTrapEngine.cs:143), so this is a latent defect being inherited AND made structurally unfixable by the new API shape. Also note §2.3 sizes D* = 157 digits for N=400 while the bake keeps only ~62 — the design's own D* is thrown away by the limb table.

[BLOCKER] Orbit overrun after a rebase turns interior pixels into uncertified black instead of terminating them
   Current: `limit = Math.Min(maxIterations - 1, reference.Length - 1)` — running out of reference simply ends the loop and the pixel is coloured as interior with `return maxIterations`. New: `limit = maxIterations - 1` and `if (referenceIndex + 1 >= orbit.Length) return NeedsMorePrecision(...)`, which escalates through every rung and ends as an unwritten black pixel (see finding 2). This is not hypothetical under rebasing: `referenceIndex = candidate` (L155) can jump forward, and the doc §3.2 explicitly requires the orbit be baked to length 2·N_max for exactly this reason — but PowerJuliaBaker.Bake:48 sets `length = iterations + 1`. NearestPointIndex's lowest-index-per-cell rule (ReferenceOrbit.cs:95) mitigates but cannot prevent it. Either bake 2·N_max as designed, or make the overrun terminate as interior the way the current engine does; silently converting it to 'unprovable' is the worst of the three.

[BLOCKER] Deleting the shallow/deep split silently re-samples every frame below zoom 45 (different pixel grid and aspect convention)
   D4 says to delete ShallowDeepThreshold and let one engine cover zoom −2 → ∞. The two engines do not sample the same points. ShaderFractalImage: `halfWidth = 2^(1-zooms)`, `invW = 2/(width-1)`, `cx = centerX + (x*invW - 1)*halfWidth` — endpoints land exactly on the view border and spacing is `2^(2-zooms)/(width-1)`. DeepOrbitTrapEngine/CertifiedRenderer: `offsetToDelta = mantissa/width`, `deltaC = (x - width/2)*offsetToDelta` — spacing `2^(2-zooms)/width`. They differ by one pixel of shear across the frame. Worse for non-square output: ShaderFractalImage applies `halfWidth` to BOTH axes with `invH = 2/(height-1)`, so a 1920x1080 frame is anisotropically stretched, while the deep path keeps square pixels. `--corruptionvideodeep` calls RenderAtZoom(zooms, 1920, 1080) for every frame, so today the video visibly changes sampling AND aspect at zoom 45; after the merge the shallow half of the film changes against the shipped reference. Also note this mismatch is silently embedded in the 0.343 baseline of `--deepcorruptioncompare`, which compares exactly these two grids (Program.cs:1147 vs 1165).

[BLOCKER] FindDeepCenter needs per-pixel escape counts and a validity flag; the new architecture exposes only an RGB buffer
   `FindDeepCenter` builds `escapeGrid[gy,gx] = isGlitch ? -1 : iters` plus `glitchGrid`, scores by 4-neighbour gradient with glitch-aware `considered` counting, tie-breaks on raw escape count, bails on `overall.escape < 0`, and adds the winning offset to the centre in BigDecimal. It is the engine behind `--deepcorruptioncenter`, which the doc's Phase 4 depends on to re-search the centre to zoom ≥ 332. CertifiedRenderer.Render returns `float[] outputRgb` + RenderStats; `PixelResult` (which carries Iterations and Verdict) never escapes CertifiedIterator, and there is no batch API that yields it. The doc is silent on this consumer. Either expose a raw `PixelResult[]` path or the search tool has to be rebuilt on colour heuristics, which the code comment at L601-607 explicitly documents as having failed before (an entire 10000-point grid tied at the same escape count).

##### SUMMARY: The §2.4 certificate is not an upper bound and the §2.1-2.3 theorems that size it do not hold for this map. Nine blocker-level defects: (1) the coupled path's Taylor truncation is never charged and §3.4's fixed |u|<1e-8 gate leaves ~1e-24 relative error, 7-38 orders above the DD/QD ulp the certificate assumes; (2) the third term ulp_table*|Z| ~ 1e-63 is ~1e37 view-widths at 10^100, so no deep pixel can pass any decision margin unless that term is common-mode - which the doc never argues, and which would in turn invalidate the D* derivation that produced it; (3) D* = 63+0.204N+12 is a measured time-average, not a bound: the doc's own escape-and-fold cycle forces single steps with |f'| = 6.1e16 (16.8 digits), overrunning the 12-digit guard; (4) N is not zoom-independent - at 10^1000 with N=400 adjacent pixels differ by 1e-922 and the frame is a flat colour, so "10^100 and 10^1000 cost the same" holds only by rendering nothing; (5) the trap-min acceptance test aggregates the wrong quantity (min is 1-Lipschitz in sup norm, so the bound is max over ALL iterations, not separation between candidates or the winner's error); (6) sensitivities are evaluated AT the computed point instead of as a sup over the uncertainty ball, so the mean-value step is invalid exactly where it matters; (7) the branch-cut choice is a discrete decision on an inexact theta across a genuine discontinuity of z^p, and a wrong choice moves delta by O(|Z^p|); (8) ColorBand's 0.75 exponent has unbounded derivative at base -> 0, so the linearised colour test can never be satisfied there and those pixels escalate forever; (9) rebasing at a 0.5 gain threshold cannot restore the coupled regime for this map (that needs |d|/|Z| < ulp^(1/3) ~ 1e-10) and, per the doc's own representation-independence theorem, cannot un-amplify error already injected - so D3's "zero repair" and §3.3's rung populations do not follow. C4's stated premise is the one claim that survives: Julia rebasing to an arbitrary Z_m is exact (cleaner than Mandelbrot, since there is no delta-c term), but the 2*N_max orbit-length bound is not a bound.
[BLOCKER] C1: the certificate has no term for the coupled path's Taylor truncation
   §2.4's recurrence has exactly three terms (amplified prior error, rung ulp on the delta, table ulp on |Z|). The coupled step d' = f'(Z)d + (1/2)f''(Z)d^2 drops O(d^3), and §3.4 fixes the gate at |u| < 1e-8. The dropped term is ~|u|^3 relative to f, i.e. 1e-24 - about 8 orders above DD's 1e-31/1e-32 and 38 orders above QD's 1e-62. Nothing in §2.4 charges it, so the certificate silently declares an error 1e8x smaller than the truth on every coupled step at DD, and 1e38x at QD. It compounds: 300 coupled steps at 1e-24 relative, each amplified by the remaining product of |f'|, is the dominant error term in exactly the regime the design claims is free. Note the code already disagrees with the doc here - PowerJuliaAtom.CoupledThresholdSquared = ulp^(2/3), i.e. |u| < ulp^(1/3), which makes the dropped term one rung ulp. Minimal correction: (a) make §3.4's gate rung-dependent, |u| < RelativeUlp^(1/3), matching the code, and (b) still add an explicit injection term C*|f'(Z)*delta|*|u|^2 (or |(1/6)f'''|*|d|^3*2^(2s)) to §2.4, because 'at most one ulp' is only a bound if it is actually charged. The same applies to the magnitude gate that skips the quadratic term (PowerJuliaAtom.cs:80): dropping it when |quad| <= ulp*|linear| injects a second full ulp that §2.4's single ulp term does not cover.

[BLOCKER] C1/C3: the ulp_table*|Z| term makes every deep pixel uncertifiable, or the D* derivation is wrong - the doc needs one and asserts both
   §2.3 sizes D* so the table's error at step n is <= 1e-63 (QD ulp) and §2.4 charges that as ulp_table*|Z| into each pixel's e. At zoom 10^100 the view is 1e-100 wide; the charged term is 1e-63, i.e. 1e37 view-widths. At 10^1000 it is 1e937 view-widths. Every escape margin (| |z|^2-1024 | > 2e|z|), every trap separation and every colour-quantisation test is then failed by an astronomical margin, so no pixel at depth can ever be certified and every pixel escalates to rung4 - the exact opposite of the claimed 75-90% at rung0/1. The render only works if that term is COMMON-MODE (the table is the exact orbit of a nearby shadow centre, so it shifts all pixels identically), but the doc never makes that argument, and it cannot: §2.3 corrects only the INITIAL rounding of the centre (the 'framing remainder'), while the per-step roundings inside the orbit iteration are not correctable that way. Pulled back to the c-plane, per-step rounding at 10^-D* is an effective centre perturbation of ~10^-157, which at 10^1000 is 1e846 pixel spacings - the frame is of an unrelated point.
